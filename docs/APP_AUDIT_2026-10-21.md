# Application audit — 21 October 2026

## Assessment

The app builds, but I would not consider the current working tree ready for a production recruitment deployment. This report identifies **28 prioritized findings: 6 P1, 20 P2, and 2 P3**, plus a cleanup backlog. The most important remaining issues concern stored-content execution, deployment configuration, ranking behavior, durable storage, and candidate-data erasure. There is also significant duplication between the Admin and recruiter workflows.

This audit reviews the current working tree, including uncommitted changes from earlier fixes. It does not assume earlier reports or passing tests prove the present behavior. No application fixes were made during this audit. New files are this report, validation logs, and isolated reproduction scripts under the ignored `scratch/audit-20261021/` directory.

Scope: API routes, authentication, parsing and screening, scoring, persistence and migrations, original-file lifecycle, cancellation, frontend state and interaction code, deployment, documentation, and automated checks. This was a source and runtime-probe audit, not a complete visual browser walkthrough, load test, external penetration test, live-provider quality benchmark, or independent compliance assessment.

Priority: **P1** = address before production use; **P2** = significant correctness, resilience, or scaling work; **P3** = maintainability and product-quality work. A deployment risk is labelled as such rather than presented as an observed production incident.

## P1 — fix before production

### 1. Interview printing inserts untrusted content as executable HTML

**Evidence:** `frontend-next/src/components/interview/interview-view.tsx:196–296`, especially the interpolated question at line 210 and `document.write` at line 255.

The print template directly interpolates question text, answers, rationale, candidate name, job title, and summary into a same-origin window. React's usual text escaping does not apply to this string. A stored job title or generated question containing HTML such as an image with an event handler is interpreted as markup when the guide is printed. The window also retains an opener reference.

**Fix:** render a print route/component using escaped text nodes, or HTML-escape every dynamic interpolation and use an appropriate restrictive content policy. Verify with hostile strings in both user-entered titles and model output.

**Reproduced:** executing the actual print handler against a synthetic window retained an event-bearing `<img>` job-title payload unchanged in the generated document. This confirms the unsafe HTML sink; it was not executed in the user's browser.

### 2. Production settings retain shared demo credentials

**Evidence:** `backend/config.py:25–30`, `backend/api/recruiter.py:83–96`, `.env.example`, `docker-compose.yml`.

Authentication is enabled, but both role passwords have public source-code defaults and demo access is enabled by default. Setting `ENVIRONMENT=production` does not disable demo access or reject default credentials. The provided Compose configuration does not supply replacement authentication settings. The login endpoint has no application-level throttling; the cookie also omits `Secure`.

**Fix:** fail production startup unless unique credentials and a stable signing secret are configured; disable demo access in production; use secure cookies over HTTPS and rate-limit login. For a shared deployment, replace role-wide passwords with individual accounts.

### 3. The Docker frontend supplies its API destination too late

**Evidence:** `frontend-next/next.config.ts:15–25`, `frontend-next/Dockerfile:1–11`, `docker-compose.yml` (`nextjs_ui.environment`).

The rewrite destination is compiled during `npm run build`. The Dockerfile builds without a backend build argument, while Compose supplies `BACKEND_API_URL=http://fastapi_backend:8000` only to the running container. With the default build context, the compiled destination is loopback inside the frontend container. The inspected production build's `routes-manifest.json` contains `http://127.0.0.1:8000/api/:path*` and the same loopback health destination.

**Impact:** a locally successful build can produce a container whose login/API calls cannot reach the backend.

**Fix:** provide the destination during the image build or implement a runtime server proxy. Validate using the actual Compose deployment, not just a local Next build.

### 4. Enabled reranking always enters the fallback branch

**Evidence:** `backend/api/recruiter.py:229,233`; `backend/config.py`.

Both reranker waits access `settings.screening_reranker_timeout_seconds`, which is not declared. The resulting `AttributeError` is swallowed by the broad reranker exception handler, so the hybrid order is retained and the model is described as unavailable/timed out. The executor submission is evaluated before the missing setting, so loading work may still be dispatched.

**Reproduced:** `hasattr(settings, 'screening_reranker_timeout_seconds') == False`.

**Fix:** declare and validate the timeout; distinguish configuration errors from expected model unavailability. Add a positive-path check proving an enabled reranker actually changes or explicitly retains results after completing prediction.

### 5. A single-CV upload reports success after durable persistence fails

**Evidence:** `backend/api/routes.py:600–626`.

`_upload_cv` logs a failed `save_candidate`, then populates memory caches and returns a successful upload response. Its caller can attach the new candidate UUID to the original-file record even though the candidate row was never saved. This produces a profile that disappears after restart and an inconsistent library link.

**Reproduced:** injecting a `RuntimeError` from `save_candidate` still returns a `CVUploadResponse` with the candidate ID.

**Fix:** return success only after candidate persistence and document linking succeed. Make a failed import retryable and clean up or reconcile vector writes that precede a failed database commit.

### 6. Permanent CV deletion can leave the raw parsing prompt behind

**Evidence:** `backend/agents/parser_agent.py:1032–1040`, `backend/services/action_logger.py:132–160`, `backend/api/routes.py:1459–1460`.

CV extraction logs contain the original CV prompt, but extraction sets action context without a candidate ID. The candidate UUID is assigned later during anonymization. `remove_candidate` erases log entries only when their string representation contains that UUID. The extraction entry therefore survives candidate deletion until buffer eviction or process restart. The logger still returns it; the action-trace route can include unscoped logs when there is no selected/default job or run.

**Fix:** assign an ingestion/document identifier before the first provider call, attach it to every prompt/result, and erase logs by explicit indexed ownership. Cover successful parsing, failed parsing, and cancellation. Do not rely on a substring search through serialized logs to establish erasure.

## P2 — correctness, resilience, and efficiency

### 7. Human corrections leave scores and gap counts inconsistent

**Evidence:** `backend/api/routes.py:921–924`.

Replacing `updated_matches` does not recompute overall/category scores or citation verification. The new gap count also counts every objective `not_met` match without checking category or active weight, so a preferred or disabled criterion can become a must-have gap.

**Reproduced:** changing a requirement from score `0.2` to `1.0` retains `overall_score=20.0` and `must_have_score=20.0`.

**Fix:** validate edited matches against the evaluation's job snapshot and recompute derived values through the shared scoring service, retaining the human decision separately.

### 8. Reloaded interview plans lose approval, draft status, summary, and tips

**Evidence:** `backend/db/models.py:209–244`, `backend/db/repository.py:502–537`, `backend/api/routes.py:171–179`.

Persistence stores questions and duration but omits `is_draft`, `hitl_approved`, the focus summary, and interviewer tips. Reconstruction restores schema defaults. An unapproved draft reloads with `is_draft=False`; an approved guide reloads with `hitl_approved=False`. The recruiter run embeds a richer second copy, so behavior also differs by retrieval path.

**Fix:** store and reconstruct the complete versioned interview contract, including approval provenance. Verify both draft and approved round trips after cache eviction.

### 9. Migration history does not describe the current evaluation model

**Evidence:** `migrations/versions/a8f316240a9e_initial_relational_schema.py:72–89`, all subsequent migrations, `backend/db/models.py:183–189`, `backend/db/session.py:107–140`.

No migration adds `llm_recommendation`, `recruiter_decision`, `evaluated_with_model`, or `evaluated_with_provider`. Startup attempts to add missing columns through a generic reconciler that silently ignores errors, bypassing Alembic revision history and constraints. Despite its SQLite name, that reconciler is called for either database engine; a PostgreSQL deployment may be repaired by it, so failure is not inevitable on every PostgreSQL instance.

**Fix:** add explicit migrations, test upgrade from an older populated schema, and stop relying on silently swallowed schema alterations. Include migrations and Alembic configuration in the backend image if it is expected to run upgrades there.

### 10. Vector-storage and embedding environment settings are ignored by default construction

**Evidence:** `backend/config.py` (`chroma_db_dir`, `embedding_model`), `backend/services/vector_store.py:20–44`, `backend/api/routes.py:75`, `backend/main.py:72–77`.

The configured path/model are not passed into the default `VectorStoreService` or embedding prewarm. Constructor defaults are hardcoded to `./data/chroma_db` and `all-MiniLM-L6-v2`.

**Impact:** changing environment configuration does not move vectors or select the requested embedding model; reported configuration can disagree with execution. This also defeats environment-only vector isolation in tests.

**Fix:** resolve defaults from the shared settings at service construction, use the same configuration for prewarm and cache keys, and reject incompatible collection/model combinations.

### 11. Database startup failures do not fail readiness

**Evidence:** `backend/main.py:30–40,164–183`.

Initialization/recovery errors are logged and startup continues. `/health` only tests `SELECT 1`, so it can return healthy with missing application columns or incomplete startup recovery.

**Fix:** fail startup for required schema initialization, or retain a failed-readiness state until schema and essential services are verified. Keep a separate lightweight liveness check if needed.

### 12. Multi-worker deployment has no shared job ownership or recovery protocol

**Evidence:** `backend/services/process_control.py:7–12`, `backend/api/recruiter.py:175–190`, `backend/db/repository.py:727–752`, `backend/config.py:30`.

Jobs, locks, cancellation registries, and ownership are process-local. Starting another worker marks all database-visible active runs/batches interrupted, including work still alive in another worker. Cancellation routed to another worker cannot stop the originating task. Without an explicitly configured signing key, workers also generate different session secrets.

**Classification:** deployment limitation; the process-control module explicitly describes a single-worker design.

**Fix:** enforce and document one backend worker until a shared queue/lease system exists. For scaling, add job leases, heartbeats, shared cancellation, versioned writes, and stable session-key configuration.

### 13. Cancellation releases admission/deletion gates before synchronous work stops

**Evidence:** `backend/services/batch_processor.py:69–77,100–109`, `backend/services/cv_library.py:29–39`, `backend/services/process_control.py:77–85`.

Cancelling an await of `asyncio.to_thread` does not terminate the synchronous function. The ingestion reader count and parser semaphore can be released while parsing or indexing continues. In particular, a cancelled indexing call can write vectors after the surrounding task has finished, and subsequent deletion/retry can overlap that write.

**Fix:** retain in-flight ownership through the end of the blocking step, or use cooperative cancellation/isolated workers. Recheck cancellation before commits and reconcile orphan vectors. The existing UI warning about a model finishing is useful but does not resolve storage ordering.

### 14. The legacy upload route bypasses the newer resource limits

**Evidence:** `backend/api/routes.py:658–681`, `backend/services/batch_processor.py:31,272–364`, `backend/api/routes.py:552–564`.

`/cv/batch-upload` reads each complete file without the new 20 MB/file, 200 MB/batch, extension, or file-count checks. Legacy batches and single uploads also bypass the global parser semaphore used by the newer parsing queue. A caller can therefore avoid the resource protections through a supported alternative endpoint.

**Fix:** route all ingress paths through one bounded validation/admission service. Enforce an infrastructure request-body limit as well as application checks.

### 15. URL fetch size checks run after the whole response is downloaded

**Evidence:** `backend/agents/job_parser_agent.py:150–198`, especially `client.get` at line 172.

The response is fully buffered before `Content-Length` or actual-body size is checked. An oversized or heavily compressed response can consume memory before the limit rejects it. DNS is also validated separately from the connection's resolution, leaving a DNS-rebinding gap despite redirect validation.

**Fix:** stream and bound decoded bytes while reading; bind the actual connection to the validated destination or enforce outbound network restrictions. Test redirects, missing lengths, oversized streaming bodies, and hostname resolution changes without contacting private infrastructure.

### 16. DOCX decompression has no expanded-size bound

**Evidence:** `backend/agents/parser_agent.py:272–309`.

Both DOCX processing paths can expand compressed XML well beyond the upload byte limit. The fallback calls `ZipFile.read('word/document.xml')` without inspecting uncompressed size. Parsing runs inside the backend process.

**Fix:** inspect archive member sizes and expansion ratios, cap expanded document text, and use time/memory isolation for untrusted document processing.

### 17. Bulk library selection has quadratic work on both sides

**Evidence:** `backend/services/cv_library.py:159`; `frontend-next/src/components/recruiter/cv-library.tsx:30–33`.

The backend rebuilds `set(ids)` inside the loop over every stored document. The frontend repeatedly searches whole record arrays for each selected ID. These patterns are particularly expensive near the advertised 50,000-ID action limit.

**Fix:** build sets/maps once; filter in SQL using bounded ID chunks; keep selection lookups constant-time. Verify with a realistically sized library.

### 18. Routine screens repeatedly load complete history

**Evidence:** `backend/api/cv_library.py:20–25`, `backend/api/recruiter.py:58,459–464`, `backend/db/models.py:149–160,201–205`, `frontend-next/src/components/recruiter/cv-library.tsx:18`.

The library returns every document every 10 seconds even while its view is hidden. Its GET also runs expiry cleanup and candidate synchronization. Statistics reads every batch progress JSON, run history has no pagination, and candidate queries eagerly load historical evaluations and plans before producing small summaries.

**Fix:** paginate/filter on the server; separate maintenance from reads; aggregate statistics in SQL; select only required summary fields; pause hidden-view polling. Measure query count and response size rather than assuming list pagination bounds backend work.

### 19. Deleting one candidate invalidates every candidate's evidence cache

**Evidence:** `backend/db/repository.py:162–221`.

Every erasure scans all run payloads and audit logs and deletes the entire `ScreeningFeatureCacheModel` table. Bulk erasure repeats this global work for each candidate. Unrelated candidates lose reusable embeddings, causing unnecessary recomputation and slowing later screening.

**Fix:** store candidate ownership on cache records, index it, and batch redaction/deletion by selected IDs. Preserve unrelated cache entries.

### 20. Shared credentials cannot establish who approved a candidate

**Evidence:** `backend/api/auth.py:19–24`, `backend/api/recruiter.py:83–95`, `backend/db/repository.py:459–494`, `backend/api/cv_library.py:155–179`.

Tokens default to the same `user_id='recruiter'`; human-decision logs store notes and decision but no actor/session provenance. Background cancellation checks authentication but does not check the recorded job scope. Any authenticated session that knows a run/batch ID can cancel it. A shared workspace may intentionally share records, but it still needs explicit authority and attributable actions.

**Fix:** introduce individual identities and explicit resource permissions; record actor, timestamp, prior/new value, and case version for approvals and destructive operations. Scope cancellation to the owner or an authorized administrator.

### 21. Compliance output declares success without running the stated checks

**Evidence:** `backend/services/compliance_service.py:143–205`, `frontend-next/src/components/compliance/compliance-dossier-modal.tsx`, `README.md`.

Article sections hardcode `COMPLIANT`, redaction claims, failover descriptions, and other assurances. They do not depend on demonstrated address redaction, complete logs, human review completion, actual failover settings, or a completed control assessment. The SHA-256 is a recomputable digest of selected evaluation fields, not an externally anchored or authenticated history of the entire dossier. The dossier alias can also be the real name because `full_name_redacted` is populated with the contact name.

**Fix:** describe the artifact as a technical evidence report; expose measured, pending, failed, and unassessed controls honestly; use neutral aliases; record the actual configuration snapshot. Treat external compliance/certification claims as requiring separate substantiation. This finding concerns software output and unsupported assertions, not a legal compliance determination.

### 22. Token analytics is session memory despite persistence claims

**Evidence:** `backend/services/token_tracker.py:131–215,309–334`; `backend/db/models.py` (`TokenUsageLogModel`).

`record_usage` appends to an in-memory list capped at 20,000 entries but does not save to the token-log table. Restarts erase real usage history, workers show different totals, and older records disappear as the cap is reached. Demo mode also seeds synthetic history by default.

**Fix:** persist usage records asynchronously through a reliable bounded queue, aggregate by database time ranges, and separate demo datasets visibly. The recruiter session-total label is more accurate than the module's persistent-analytics description.

### 23. Multiple writable copies allow decisions and job drafts to disagree

**Evidence:** `backend/api/recruiter.py:505–530`, `backend/api/routes.py:893–962`, `frontend-next/src/components/recruiter/jobs.tsx:76–85`, `frontend-next/src/components/recruiter/workspace.tsx:229–236`.

Human decisions live in both evaluation rows and screening-run JSON. Admin validation updates the evaluation without synchronizing existing run copies. Saved job editors are initialized once from props and remain mounted; a subsequent external/Admin update does not refresh a clean draft, and saving can overwrite newer data. There is no optimistic revision check.

**Fix:** give evaluations and jobs explicit versions; keep one authoritative decision record; derive or update snapshots transactionally; refresh clean drafts on version changes and detect conflicting saves.

### 24. Personal CV data remains in browser storage after logout

**Evidence:** `frontend-next/src/components/pipeline/pipeline-view.tsx:118–170`, `frontend-next/src/app/page.tsx:20–23`, `frontend-next/src/components/layout/shell.tsx:174–183`.

Admin upload responses containing parsed/raw CV data are saved under `atos_pipeline_single_extraction` in `localStorage`. Logout clears the query cache but leaves this storage entry. A later Admin session in the same browser restores the previous candidate's document, even if it was removed elsewhere. The storage is not account-scoped.

**Fix:** avoid persisting document bodies in browser storage; persist an identifier and refetch under current authorization. Clear sensitive state on logout and erasure, and scope any remaining workspace state by identity.

### 25. The shipped Streamlit UI cannot authenticate to the protected API

**Evidence:** `frontend/api_client.py:26–89`, `docker-compose.yml` (`streamlit_ui`), `backend/api/auth.py:88–94`.

The legacy client's requests create new HTTP clients with no session cookie, bearer token, or login flow. Authentication is now required by default. Its health request can succeed while candidate, job, evaluation, and settings requests receive 401 responses. Compose still builds and starts this UI as a supported service.

**Fix:** retire the redundant UI from default deployment or implement a proper authenticated session flow. Do not work around this by globally disabling backend authentication.

### 26. Local-model management can block the entire API event loop

**Evidence:** `backend/api/routes.py:2353–2365,2402–2424`; `backend/services/ollama_service.py:444–510`.

Async endpoints call synchronous status/start/load/unload/pull methods directly. These methods use blocking HTTP clients or sleep loops. Loading has a 60-second timeout and pulling has a 300-second timeout. While a request is blocked there, the same event loop cannot serve unrelated health, recruiter, progress, or cancellation requests. Some adjacent hardware/model-list routes already offload correctly, so this is an inconsistent implementation rather than a limitation of FastAPI.

**Fix:** use async network clients or bounded worker tasks; make downloads durable background jobs with progress and cancellation. Verify health and normal recruiter requests remain responsive during a simulated slow model operation.

## P3 — professional product and engineering quality

### 27. Automated quality gates do not cover the actual workflow risks

**Evidence:** `frontend-next/package.json`, `frontend-next/eslint.config.mjs`, `tests/conftest.py:20–24`, validation logs.

The frontend utility tests pass but are not exposed through a package test script. Lint fails with 146 errors and 91 warnings; some are configuration mismatches for `.cjs` tests, while others affect application code. Most backend tests disable authentication automatically. One backend test still expects an objective rejection for missing location/work-authorization evidence, conflicting with the current clarification policy. No checked-in CI workflow was found.

**Fix:** establish CI for backend tests, frontend tests, lint, build, and migration upgrades. Add focused end-to-end coverage for login → upload → restart → screening → correction → approval → interview → erasure, including authenticated requests. Resolve lint categories deliberately rather than disabling all rules.

### 28. The compliance modal lacks the native-dialog behavior used elsewhere

**Evidence:** `frontend-next/src/components/compliance/compliance-dossier-modal.tsx:88` and component event handling; compare recruiter `ProfileDialog`/`StatisticsDialog`.

The modal is a fixed overlay `div` without dialog semantics, managed focus containment/return, or an Escape handler. Keyboard focus can remain behind the overlay. This differs from the newer recruiter dialogs, which use `showModal()`.

**Fix:** reuse an accessible native-dialog wrapper or one tested shared dialog component, including its accessible name and keyboard behavior. Verify keyboard-only open, navigation, close, and return focus.

## Additional cleanup and product backlog

- **Consolidate ingestion:** single upload, legacy batch screening, cohort parsing, and library preparation implement overlapping validation and lifecycle rules. Share the service and retain thin endpoint adapters.
- **Consolidate frontend state:** Admin mixes localStorage and local state with query-cached recruiter views. Centralize invalidation and case identity instead of maintaining parallel caches and embedded results.
- **Bound mounted views:** every visited job keeps its editors, verification, comparison, and interview views mounted. Preserve active tasks/drafts in a store, but unmount inactive heavy views and stop their polls.
- **Make partial extraction visible:** PDFs stop at 20 pages; model extraction silently trims to 6,500 characters for Ollama or 35,000 otherwise, with a 5,000-character retry. Full raw text is retained after model parsing and deterministic enrichment recovers some details, but that does not guarantee all omitted experience is structured. Surface coverage warnings and process long documents in bounded sections.
- **Improve provider error handling:** recruiter draft extraction catches `ValueError` but temporary provider exhaustion is a different exception; other endpoints handle this with 503/Retry-After. Standardize retryable error contracts and show meaningful recovery guidance.
- **Make job selection scale:** candidate search/cohort selection only covers the current 100-profile library page. The UI discloses this, so it is a limitation rather than a hidden global-search bug. Add server-side search and explicit cross-page cohort selection for large libraries.
- **Harden packaging:** backend image copies `data/` into the image; no `.dockerignore` was found. Avoid baking applicant files into images. Split runtime/dev/evaluation dependencies and pin a reproducible Python dependency set; avoid always launching the legacy Streamlit UI and tracing service when unused.
- **Update documentation:** README still states 74 tests, has outdated model/startup claims, and presents certification-style assurances the implementation does not verify. Keep validation counts generated or timestamped and align the deployment guide with actual image configuration.
- **Repair progress contracts:** the newer parse-batch service updates database progress without publishing the SSE events emitted by the legacy batch processor. Existing polling makes the recruiter view work, but an SSE subscriber attached to a new active batch can receive initial state and heartbeats without completion. Either publish a common event stream or retire/document that endpoint's narrower support.
- **Avoid killing unrelated services:** `start_enterprise.py:kill_process_on_port` force-kills whatever owns a configured port if its health check fails. Verify process identity or provide a non-destructive failure message before terminating a potentially unrelated application.

## Recommended order

1. Close the HTML injection and insecure production defaults; fix Docker proxy configuration.
2. Repair reranking, upload durability, corrected-score calculation, and full interview persistence.
3. Complete trace ownership/erasure and sensitive browser-state cleanup; make control reports factual.
4. Establish explicit schema migrations, readiness checks, individual identities, and a documented single-worker deployment boundary.
5. Unify ingestion/cancellation rules, add resource limits, and eliminate whole-history/quadratic work.
6. Make CI green and add lifecycle integration tests before polishing the remaining UI and documentation.
